# 3. Main objective: complete editing functionality

The Build mode must behave like a genuine city editing tool.

## A. Object deletion

If not already implemented, add:

- Delete action in the contextual inspector.
- Delete action through keyboard shortcuts.
- Delete selected object.
- Clear selection after deletion.
- Correct handling of dependent references.
- Undo support.
- Redo support.
- Protection against deleting required infrastructure when that would leave invalid project state.

Keyboard shortcuts:

- Delete or Backspace: delete selected object.
- Ctrl+Z: undo.
- Ctrl+Y or Ctrl+Shift+Z: redo.
- Escape: cancel active placement or editing operation.

Avoid browser shortcuts conflicting with application behavior.

Ensure keyboard shortcuts do not interfere with text inputs, textareas, or editable form controls.

## B. Road construction

Improve the road-building system.

The current implementation was previously found to create limited fixed-direction road segments. Verify whether that remains true.

If confirmed, implement:

1. Select road tool.
2. Choose a starting point on the ground plane.
3. Choose an endpoint.
4. Preview the proposed road.
5. Confirm placement.
6. Validate road geometry.
7. Connect compatible endpoints.
8. Update the road graph.
9. Support road selection and editing.
10. Support road deletion and undo.

Road configuration should support:

- Road type.
- Number of lanes.
- Speed limit.
- Direction.
- Open/closed status.

Consider snapping to existing road endpoints and intersections.

Avoid introducing complex curved-road functionality unless it can be implemented reliably within the scope. Clearly separate straight-road support from any future curved-road capability.

## C. Intersection validation

Roads must connect cleanly.

Define validation rules for:

- Compatible road widths.
- Valid connection endpoints.
- Duplicate segments.
- Invalid geometry.
- Disconnected road segments.
- Road graph consistency.

Do not allow the user to create a road that visually connects but is missing from the simulation graph.

# 4. Project persistence and data safety

This is a high-priority correctness requirement.

## A. Local project loading

Ensure localStorage projects pass the same comprehensive validation used for JSON imports.

Validate:

- Project schema.
- Project version.
- Object IDs.
- Object types.
- Numeric ranges.
- Required fields.
- Road references.
- Vehicle references.
- Scenario references.
- Event target references.
- Module configuration.

A corrupted or unsupported project must not overwrite the current valid project.

## B. Referential integrity

Implement checks for relationships such as:

- Vehicle `spawnRoadId` references an existing valid road.
- Incident `roadId` references an existing valid road.
- Scenario events reference existing supported targets.
- Selected object IDs refer to existing project objects.
- Road graph references valid road entities.

Use the actual project types and schema rather than inventing new fields.

## C. Import and export

Support:

- Valid JSON import.
- Invalid JSON rejection.
- Unsupported version rejection.
- Clear error messages.
- Safe loading.
- Correct round-trip serialization.

Verify that exporting and then importing a project preserves its important properties and relationships.

## D. Persistence testing

Add tests for:

- Save and reload.
- Import and export.
- Invalid JSON.
- Invalid object references.
- Unsupported schema versions.
- Corrupted localStorage data.
- Recovery without losing the current project.

# 5. Improve the visual environment without compromising performance

The current procedural rendering approach is intentional. Do not replace it with a large collection of expensive models.

Improve visual quality selectively.

Priority order:

1. Roads and lane markings.
2. Intersections.
3. Building variety.
4. Vehicle silhouettes.
5. Traffic signals.
6. Trees and street furniture.

## Visual direction

Follow the approved CityFluxy references:

- Dark slate and navy interface.
- Restrained cyan and violet highlights.
- Semi-realistic stylized city.
- Realistic urban proportions.
- Clearly visible roads and intersections.
- Modern architectural variety.
- Natural vegetation.
- Minimal decorative effects.
- Clean professional workspace.

Do not introduce:

- Cyberpunk styling.
- Excessive neon.
- Unnecessary holograms.
- Unnecessary post-processing.
- Expensive high-resolution textures.
- Decorative UI elements that do not provide information.

Use procedural geometry and instancing wherever practical.

GLB assets may be considered only when they offer meaningful visual improvement without excessive performance cost.

Pedestrian support should be proposed as a separate optional capability if it requires substantial changes to the simulation model. Do not add decorative pedestrian models that have no meaningful behavior.

# 7. Performance requirements

The target development hardware is:

- Intel Core i3-7100.
- 8 GB RAM.
- NVIDIA GT 710 with 2 GB VRAM.
- Windows 11.

Define initial performance targets as measurable engineering goals, not guaranteed results.

Recommended starting targets:

- Aim for approximately 30 FPS at the low-quality preset.
- Keep low-quality rendering usable during normal editing.
- Limit active vehicle counts according to quality settings.
- Avoid per-vehicle React state updates every frame.
- Use instancing for repeated objects.
- Keep real-time shadows disabled in low quality.
- Avoid unnecessary post-processing.
- Avoid excessive draw calls.
- Provide quality settings that actually affect rendering.

Document the methodology for benchmarking.

Distinguish measured results from estimated targets.

Do not claim that performance has been verified on the target PC unless a real measurement has been performed on that machine.

# 9. Architecture preservation requirements

The original implementation established important architectural boundaries.

Preserve these:

1. The simulation engine must remain independent of React, Three.js and browser APIs.
2. Rendering must consume simulation output.
3. Simulation logic must not be duplicated inside visual components.
4. Zustand stores must retain clear responsibilities.
5. Road graph data must remain derived or consistently synchronized with the authoritative project data.
6. Undo/redo must preserve project consistency.
7. Local persistence must remain independent of future backend interfaces.
8. AI and backend ports must remain disconnected.
9. Quality settings must control actual rendering behavior.
10. Simulation results and analytics must use the same authoritative simulation state.

Do not refactor working architecture merely to make the code look different.
