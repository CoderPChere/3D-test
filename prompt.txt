# OpenSpec Proposal: Transform CityFluxy into a Modular 3D Simulation Sandbox

## Your Role

Act as a senior software architect and technical product engineer.

You are working on an existing project called **CityFluxy**, a 3D city and mobility visualization application built with Next.js, React, Three.js, React Three Fiber, Drei, Tailwind CSS, and Framer Motion.

---

# 1. Product Vision

Transform CityFluxy from its current scroll-driven 3D city experience into a reusable, interactive simulation workspace.

The application should let users:

- Explore a procedurally generated 3D city.
- Select and inspect city objects.
- Build and modify city infrastructure.
- Create and edit simulation scenarios.
- Run local traffic simulations.
- Observe simulation metrics and visualizations.
- Save and load projects locally.
- Export and import project data.

The long-term objective is to create a reusable frontend sandbox architecture that can be adapted for different hackathon problem statements, particularly in mobility, smart cities, infrastructure, logistics, environmental monitoring, and related spatial simulation domains.

**Important:** Do not claim that one unchanged application can solve every possible hackathon problem statement. The reusable part should be the simulation workspace, rendering engine, interaction system, state management, persistence, and module architecture. Domain-specific modules and simulation rules will still need to change.

---

# 2. Strict Technical Constraints

The current version must work entirely in the browser.

## Absolutely no backend or connected AI

Do not implement or depend on:

- Backend servers.
- REST or GraphQL APIs.
- Database services.
- Authentication servers.
- AI model APIs.
- LLM integrations.
- Live traffic APIs.
- External city data services.
- API keys or environment-based service credentials.
- Paid or externally hosted infrastructure.

All current functionality must work using local application state, deterministic simulation logic, demo data, and browser storage.

Future integration points may be defined through TypeScript interfaces, but they must remain disconnected.

## Existing technology stack

Preserve the existing stack wherever practical:

- Next.js
- React
- TypeScript
- Three.js
- React Three Fiber
- Drei
- Tailwind CSS
- Framer Motion
- GSAP, where justified

Zustand may be proposed for application state management if the existing architecture would benefit from it. It is not currently installed, so account for the dependency explicitly.

Do not introduce large libraries without explaining their necessity.

# 6. Architecture to Propose

Design the application as independent but connected layers.

## A. Rendering layer

Responsible for:

- Three.js scene.
- Camera.
- Lighting.
- City geometry.
- Roads.
- Buildings.
- Vehicles.
- Infrastructure objects.
- Visualization layers.

Rendering must remain separate from simulation logic.

## B. Interaction layer

Responsible for:

- Selection.
- Object placement.
- Object movement.
- Object deletion.
- Editing tools.
- Keyboard shortcuts.
- Undo and redo.
- Contextual inspector behavior.

## C. Simulation engine

Create a standalone TypeScript simulation engine independent of React and Three.js.

It should be responsible for:

- Fixed-timestep simulation.
- Deterministic random seed.
- Vehicle spawning.
- Vehicle movement.
- Vehicle following behavior.
- Traffic signals.
- Road capacity.
- Congestion and queues.
- Road closures.
- Incident handling.
- Alternative route calculation.
- Simulation metrics.

The rendering layer should consume simulation output. It should not own the simulation rules.

Avoid updating React state for every vehicle on every animation frame. Propose efficient approaches such as refs, instanced meshes, and batched updates.

## D. State management

Propose a clean separation between:

- Application state.
- City/project state.
- Selection and interaction state.
- Simulation state.
- Scenario state.
- Settings state.

Evaluate Zustand for this purpose.

## E. Scenario management

Users should be able to:

- Create scenarios.
- Rename scenarios.
- Duplicate scenarios.
- Add events.
- Schedule events.
- Run scenarios.
- Reset scenarios.
- Compare scenario results.

Example events:

- Road closure.
- Traffic accident.
- Vehicle surge.
- Signal timing change.
- Infrastructure modification.

## F. Local persistence

Implement the architecture for:

- Save project locally.
- Load project locally.
- Export project as JSON.
- Import project from JSON.
- Validate imported project data.
- Persist basic settings.

Use localStorage for small project data. Consider IndexedDB only if there is a clear need.

## G. Future integration contracts

Propose disconnected TypeScript interfaces for future integration.

For example:

`BackendPort.ts`

- Save project.
- Load project.
- List projects.
- Save scenarios.

`AIProviderPort.ts`

- Generate scenario.
- Explain simulation.
- Recommend improvements.

`DataProviderPort.ts`

- Retrieve city data.
- List available cities.

These are interfaces only. Do not implement network calls, mock AI responses, or provider-specific integrations.

The current application must function without these adapters.

# 7. Modular Domain Architecture

Propose a module registry that allows the workspace to enable different domain capabilities.

Potential modules:

- Mobility.
- Infrastructure.
- Environment.
- Public safety.
- Logistics.

Each module should be able to declare:

- Module ID.
- Display name.
- Enabled state.
- Available tools.
- Supported object types.
- Visualization layers.
- Metrics.
- Relevant simulation capabilities.

Example conceptual interface:

```ts
export interface SandboxModule {
  id: string;
  name: string;
  enabled: boolean;
  tools: string[];
  objectTypes: string[];
  visualizationLayers: string[];
  metrics: string[];
}
```

Do not over-engineer a generic plugin framework. Propose only the abstraction needed for the current product and realistic future extensions.

- 8 GB RAM.
- NVIDIA GT 710 with 2 GB VRAM.

Propose:

- Instanced vehicle rendering.
- Merged static geometry.
- Limited real-time shadows.
- Low/medium/high quality settings.
- Adaptive device pixel ratio.
- Distance-based level of detail.
- Minimal post-processing.
- Efficient simulation updates.
- Controlled entity counts.

Do not prioritize graphical complexity over responsiveness.

Include a performance testing strategy for this hardware class.

# 11. Critical Acceptance Criteria

The proposal must define how we will verify the following:

1. The application starts without backend services or API keys.
2. The primary experience opens directly into the simulation workspace.
3. The 3D scene is interactive.
4. Users can select and inspect objects.
5. Users can place and edit supported city objects.
6. The simulation can play, pause, and reset.
7. Simulation behavior is deterministic when using the same seed and inputs.
8. Scenarios can be created and modified locally.
9. Metrics are calculated from actual local simulation state, not hardcoded display values.
10. Projects can be saved and restored locally.
11. JSON import/export works with validation.
12. No active UI control is merely decorative.
13. No connected AI, backend, database, or live-data service is required.
14. Future integrations remain isolated behind interfaces.
15. The application has a documented strategy for running on low-end hardware.

# 12. Important Engineering Rules

- Inspect before proposing.
- Do not rewrite the entire project without a migration rationale.
- Do not introduce unnecessary abstractions.
- Do not mix simulation logic with React components.
- Do not make the Three.js scene responsible for application state.
- Do not use random values that make the same simulation produce unpredictable results.
- Do not hardcode simulation metrics.
- Do not create fake AI features.
- Do not create fake live traffic data indicators.
- Do not add backend dependencies.
- Do not sacrifice usability for visual effects.
- Do not create tasks that are too large to verify.
- Do not claim functionality exists when it is only proposed.

If a requirement is technically risky, ambiguous, or too large for the initial version, explicitly flag it and recommend a smaller implementation.
